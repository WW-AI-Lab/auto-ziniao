# 操作节奏与流程稳定性规划

> 本文评估当前 flow 设计、TypeScript 引擎与未来扩展中对"操作节奏、频率控制、人工确认、异常停止"的支持情况，并给出后续最佳实践与分阶段实现规划。
>
> 边界说明：本文聚焦操作节奏、流程稳定性、确认门槛与可审计执行，不展开浏览器指纹、平台识别或外部风控策略。目标是避免因高频、重复、误点、并发、无确认写操作造成店铺运营风险。

## 结论摘要

当前仓库已经有基础的等待与重试能力，但尚未形成统一的“操作节奏层”：

- 已有能力：
  - flow 顶层 `retry.delayMs` 支持流程级重试等待。
  - step 级 `on_fail.retry.delayMs` 支持失败后的本步骤等待重试。
  - 内置 `sleep` action 支持流程作者手写固定等待。
  - ZClaw 工具参数普遍可传 `timeoutMs`，用于等待页面/元素/导航结果。
  - `branch`、`validate`、`assert` 可避免页面状态不满足时继续误操作。
- 主要缺口：
  - 没有全局 pacing policy，所有节奏依赖 flow 作者手写。
  - 没有按店铺、按站点、按 flow、按工具类型的速率预算。
  - 没有“读操作/写操作/高影响操作”的动作分级。
  - 没有统一的操作前后最小间隔、暂停窗口、每日执行上限和并发限制。
  - 没有系统化的人机确认门槛，例如提交、保存、批量修改、删除、发货等动作。
  - 当前 ZClaw 工具层以语义工具为主，没有低层鼠标轨迹抽象，也不应把“随机鼠标”作为核心策略。

推荐方向：不要把重点放在“随机鼠标移动”这类低价值、难审计、易失控的表层拟人化上；应该建设“可声明、可审计、可测试”的操作节奏与风险分级系统。核心是限速、分级、确认、状态校验、幂等、并发隔离和异常停止。

## 当前实现评估

### flow DSL

当前 `docs/03-流程定义规范.md` 定义的节奏相关字段主要有：

| 位置 | 字段 | 当前作用 | 局限 |
|------|------|----------|------|
| 顶层 | `retry.maxAttempts` / `retry.delayMs` | 整个流程失败后重试 | 固定延迟，无全局预算和退避策略 |
| step | `on_fail.retry.maxAttempts` / `delayMs` | 单步骤失败重试 | 只在失败后等待，无法约束正常操作间隔 |
| step | `action: "sleep"` / `seconds` | 手写等待 | 依赖作者经验，无法统一审计 |
| tool args | `timeoutMs` | 等待工具完成或元素出现 | 是等待结果，不是操作频率控制 |
| step | `branch` / `condition` / `validate` | 页面状态判断与防空数据 | 可降低误操作，但不表达操作风险等级 |

现有 `flows/*.json` 大多使用 1 到 4 秒固定 `sleep`，失败重试多为 2 到 5 秒固定 `delayMs`。这足够支撑 demo 和低频读取类任务，但不足以支撑多店铺、多 flow、定时任务和写操作场景。

### TypeScript 引擎

`packages/flow-engine` 当前执行模型是顺序步骤循环：

1. 判断 `condition`。
2. 执行 `branch` / `goto`。
3. 执行 ZClaw tool 或内置 action。
4. 保存结果、校验、跳转。
5. 失败时按 `on_fail` 重试、分支或触发自愈。

这里没有统一的操作调度器。任何 `click_element`、`input_text`、`scroll_page`、`execute_script`、`run_automation` 都会在步骤轮到时立即调用 ZClaw bridge。`sleep` 只是一个普通 action，不会自动插入到工具调用前后。

### ZClaw client

`packages/zclaw` 的职责是：

- 读取 API key。
- 限制请求路径只能是 `/zclaw/*`。
- 调用 `GET /zclaw/tools` 与 `POST /zclaw/tools/invoke`。
- 封装 `open_store`、`visit_page`、`execute_script`、`click_element`、`wait_for_element` 等工具。

ZClaw client 当前不维护操作节奏状态，也不记录“上一次对某店铺执行了什么操作”。这符合它作为底层 bridge client 的定位，但意味着 pacing 不应该散落在 client 里硬编码；更合适的位置是 flow-engine 的执行调度层。

### 工程包结构

当前 TypeScript 工程结构：

- `packages/core`：无浏览器副作用基础工具。
- `packages/schemas`：flow 契约和静态校验。
- `packages/zclaw`：TS 侧唯一 ZClaw bridge client。
- `packages/flow-engine`：流程引擎。
- `packages/self-heal`：自愈触发器。
- `packages/cli`：生产 CLI 入口。
- `apps/api`：WebAdmin 后端。
- `apps/web`：WebAdmin 前端。

操作节奏能力应优先在 `packages/flow-engine` 的执行调度层中设计，而不是在 `packages/zclaw` 中隐式实现。原因是：

- 节奏策略依赖 flow、step、店铺、动作类型和调度上下文，超过了 bridge client 的职责。
- 测试需要使用 mock sleeper / fake clock 做离线验证，放在 flow-engine 更自然。
- 后续 self-heal、cli、webadmin 都应复用同一套策略，不应各自实现。

## 最佳实践

### 1. 把操作分级，而不是只给步骤加 sleep

建议将步骤按业务影响分为四类：

| 等级 | 示例 | 默认处理 |
|------|------|----------|
| `read` | 访问页面、等待元素、读取文本、截图、提取数据 | 可自动执行，需基础间隔和超时 |
| `navigate` | 打开店铺、跳转页面、切换 tab/入口 | 自动执行，但需等待页面稳定 |
| `write` | 输入、点击保存、筛选提交、下载、批量操作入口 | 需要更长前后间隔、状态确认和结果校验 |
| `critical` | 删除、提交订单处理、财务/物流确认、批量修改、不可逆动作 | 默认需要人工确认或显式 allowlist |

flow 不应只表达“调用了哪个工具”，还应表达“这一步的业务影响是什么”。例如：

```json
{
  "id": "apply_filter",
  "tool": "click_element",
  "risk": "write",
  "args": { "selector": "button[type=submit]" },
  "validate": { "contains": "筛选结果" },
  "on_fail": { "action": "heal", "context": "element_not_found" }
}
```

短期可以先作为约定写入文档和 `heal.hints`；真正校验等 M3 或独立 OpenSpec change 再落地。

### 2. 默认使用语义等待，不依赖固定睡眠

固定 `sleep` 适合作为兜底，但不应成为主要同步方式。优先顺序应是：

1. `wait_for_element` 等待目标元素可见或可用。
2. `wait_for_navigation` 等待页面跳转完成。
3. `execute_script` 读取页面状态，例如表格行数、加载遮罩是否消失。
4. 最后才使用短 `sleep` 作为 UI 动画、异步渲染的缓冲。

推荐沉淀 flow 时，每个关键点击后都配一个明确的成功条件：

```json
{
  "id": "click_orders_menu",
  "tool": "click_element",
  "risk": "navigate",
  "args": { "selector": "a[href*='orders']" },
  "on_fail": { "action": "retry", "delayMs": 3000, "maxAttempts": 2, "context": "element_not_found" }
},
{
  "id": "wait_orders_table",
  "tool": "wait_for_element",
  "risk": "read",
  "args": { "selector": "table", "state": "visible", "timeoutMs": 30000 },
  "on_fail": { "action": "heal", "context": "timeout" }
}
```

### 3. 对写操作建立确认门槛

任何会改变店铺状态的操作都应满足三个条件：

- 操作前确认：页面、店铺、账号、目标对象、数量、金额、状态均符合预期。
- 操作中限速：写操作前后有更长间隔，不与同店铺其他 flow 并发。
- 操作后验证：验证页面结果、toast、列表状态或导出结果，不把“点击成功”当作业务成功。

建议新增 flow 约定：

```json
{
  "id": "confirm_before_submit",
  "action": "assert",
  "risk": "critical",
  "value": "${precheck.can_submit}",
  "expected": true,
  "check": "eq",
  "on_fail": { "action": "abort", "context": "precheck_failed" }
}
```

对 `critical` 级操作，默认策略应是：

- 默认不允许定时无人值守执行。
- 需要运行参数显式开启，例如 `-p allow_critical=true`。
- WebAdmin 中应显示待确认任务，而不是直接执行。
- 自愈 Agent 不得自动修复为“跳过确认继续提交”。

### 4. 按店铺做串行化和预算

多店铺任务可以并行，但同一店铺应默认串行。原因不是技术限制，而是业务状态一致性：

- 两个 flow 同时操作同一店铺，可能互相切页面、切筛选条件、覆盖输入。
- 重试和自愈可能放大重复点击。
- 定时任务和人工手动运行可能撞车。

建议目标态引入 per-store execution lock：

```text
store lock key = storeId 或 storeName
同一 store key 同一时刻只允许一个 flow run 持有锁
锁超时后自动释放，但运行日志标记异常释放
```

预算建议：

| 维度 | 策略 |
------|------|
| 单店铺 | 同一时间只运行一个 flow |
| 单 flow | 默认禁止同 flow 重入 |
| 单工具 | `click_element` / `input_text` / `scroll_page` 设置最小间隔 |
| 单日 | 每店铺每日最大 flow 次数和最大写操作次数 |
| 失败 | 连续失败达到阈值后熔断，不继续重试 |

### 5. 使用可审计的节奏策略，而不是不可解释的随机行为

“随机鼠标移动”不是当前系统应优先建设的能力：

- 当前 ZClaw 工具列表没有低层 mouse move 工具，臆造工具名违反仓库规则。
- 低层轨迹难以离线测试，失败时也难以复盘。
- 随机行为会降低可重复性，与“0 tokens 可重复执行流程”的目标冲突。

更合适的策略是“带边界的节奏策略”：

- 每类操作有最小间隔、最大间隔、超时、重试次数。
- 抖动只用于避免所有任务在同一毫秒同时触发，不用于隐藏行为。
- 抖动范围必须可配置、可记录、可复现；测试中用固定 seed 或 fake clock。
- 每次等待在日志中记录原因，例如 `before_write_min_interval`、`after_navigation_stabilize`。

推荐概念模型：

```json
{
  "pacing": {
    "profile": "standard",
    "jitter": { "enabled": true, "ratio": 0.15 },
    "limits": {
      "perStoreConcurrency": 1,
      "maxConsecutiveFailures": 3
    },
    "defaults": {
      "read": { "beforeMs": 300, "afterMs": 500 },
      "navigate": { "beforeMs": 800, "afterMs": 1500 },
      "write": { "beforeMs": 1500, "afterMs": 3000 },
      "critical": { "requiresConfirm": true, "beforeMs": 3000, "afterMs": 5000 }
    }
  }
}
```

这里的数值只是契约草案，不应在未验证业务场景前直接作为强制默认值。

### 6. 建立异常停止，而不是无限自愈

自愈的目标是修复流程，不是继续推进不确定操作。建议约束：

- `auth_failed`、权限不足、风控提示、账号异常、二次验证页面：立即停止，要求人工处理。
- 页面出现确认弹窗且目标不明确：停止，不自动点击确认。
- 写操作后无法验证结果：标记为 `unknown_outcome`，不要重试同一写操作。
- 同一步骤连续失败：熔断并写入运行日志。
- 同一店铺同一 flow 当日失败超过阈值：暂停该 flow 的定时执行。

## 目标态契约草案

建议将 pacing 分为三层：全局默认、flow 覆盖、step 覆盖。

### 顶层 flow pacing

```json
{
  "id": "orders_overview",
  "pacing": {
    "profile": "standard",
    "perStoreConcurrency": 1,
    "maxRunPerDay": 24,
    "maxConsecutiveFailures": 3,
    "jitter": { "enabled": true, "ratio": 0.1 }
  }
}
```

### step 风险等级

```json
{
  "id": "input_keyword",
  "tool": "input_text",
  "risk": "write",
  "pacing": {
    "beforeMs": 1200,
    "afterMs": 1800
  },
  "args": {
    "selector": "input[name=keyword]",
    "text": "${params.keyword}"
  }
}
```

### critical 确认门槛

```json
{
  "id": "submit_bulk_change",
  "tool": "click_element",
  "risk": "critical",
  "confirm": {
    "required": true,
    "message": "确认提交批量修改",
    "allowParam": "allow_critical"
  },
  "args": { "selector": "button.submit" },
  "validate": { "contains": "提交成功" }
}
```

### 运行日志扩展

建议将 pacing 决策写入 `data/logs/runs.jsonl` 或独立 event log：

```json
{
  "event": "pacing_wait",
  "flow_id": "orders_overview",
  "step_id": "open_orders",
  "store_id": "xxx",
  "reason": "after_navigation_stabilize",
  "wait_ms": 1450,
  "profile": "standard"
}
```

这对后续排查“为什么慢”“为什么停”“是否重复点击”很重要。

## 分阶段规划

### P0：立即执行的流程编写约定

不改代码，先更新团队沉淀习惯：

- 新 flow 必须为每个点击、输入、提交步骤写清 `heal.hints` 中的业务意图。
- 点击后必须有 `wait_for_element`、`wait_for_navigation`、`validate` 或 `assert`。
- 写操作前必须有状态读取和断言。
- 固定 `sleep` 只能作为兜底，不作为唯一成功判断。
- 定时任务默认只跑读取类 flow；写类 flow 需单独评审。

### P1：OpenSpec 提案

新增 change，建议名：`add-flow-pacing-policy`。

范围：

- 扩展 flow schema：`pacing`、`risk`、`confirm`。
- 更新 `docs/03-流程定义规范.md`。
- 增加静态校验：
  - `critical` 步骤必须有 `confirm` 或显式豁免。
  - `click_element` / `input_text` / `run_automation` 未声明 `risk` 时给 warning。
  - 写操作后缺少 validate/assert/wait 时给 warning。
- 增加离线 fixtures 和 golden 测试。

不在 P1 做真实 ZClaw 调用。

### P2：M3 Flow Engine 中实现 pacing runtime

范围应限制在 `packages/flow-engine`：

- `PacingPolicyResolver`：合并全局默认、flow、step 策略。
- `PacingScheduler`：根据 step risk、store key、上次操作时间计算等待。
- `Sleeper` 接口：生产用真实 sleep，测试用 fake sleeper。
- `StoreLock` 接口：先做进程内锁，后续再评估文件锁或 SQLite。
- `ConfirmGate`：critical 步骤默认要求参数显式授权。
- 日志事件：记录每次 pacing wait、confirm reject、budget reject。

默认测试仍使用 mock ZClaw client，不调用真实 bridge。

### P3：Pacing 运行时集成（已部分实现）

`packages/flow-engine` 已具备基础 `Sleeper` 接口和 mock sleeper 测试能力。后续 pacing 运行时可直接在 flow-engine 中扩展：

- `PacingPolicyResolver`：合并全局默认、flow、step 策略。
- `PacingScheduler`：根据 step risk、store key、上次操作时间计算等待。
- `StoreLock` 接口：进程内锁（已在 WebAdmin 调度器中实现）。
- `ConfirmGate`：critical 步骤默认要求参数显式授权。
- 日志事件：记录每次 pacing wait、confirm reject、budget reject。

默认测试使用 mock ZClaw client，不调用真实 bridge。

### P4：WebAdmin 观测与人工确认

WebAdmin 后续应承担人工确认和观测，而不是让 CLI 承载所有交互：

- flow 列表显示 risk 分布。
- run 详情显示 pacing wait 事件。
- critical 步骤进入“待确认”状态。
- 支持暂停某店铺/某 flow 的计划任务。
- 连续失败或 unknown outcome 自动标记为需人工复核。

## 新 flow 沉淀检查清单补充

在 `docs/03-流程定义规范.md` 的现有 Checklist 基础上，建议增加：

- [ ] 每个点击/输入/提交步骤标注业务意图和风险等级。
- [ ] 点击后有明确成功条件，不只依赖 `sleep`。
- [ ] 写操作前有状态读取和断言。
- [ ] 写操作后有业务结果验证。
- [ ] 不可逆或批量操作默认不进入无人值守 schedule。
- [ ] 同一店铺的定时 flow 不重叠。
- [ ] 连续失败、未知结果、账号异常类页面立即停止。
- [ ] `heal.hints` 明确哪些按钮不能由自愈自动点击。

## 推荐默认策略

短期在文档和人工 review 中采用以下默认：

| 场景 | 推荐策略 |
|------|----------|
| 读取报表/列表 | 自动执行，页面稳定后提取，validate 防空 |
| 翻页/筛选 | 自动执行，但每步后等待结果区域变化 |
| 输入搜索条件 | 写等级处理，输入前确认页面和字段，输入后等待结果 |
| 下载文件 | 写等级处理，下载后校验文件存在和大小 |
| 保存配置 | critical，默认人工确认 |
| 批量修改 | critical，默认人工确认，不进无人值守 schedule |
| 删除/取消/提交 | critical，默认人工确认，并要求结果可验证 |
| 出现二次验证/异常提示 | 立即停止，记录截图和页面文本 |

## 与现有执行边界的关系

操作节奏规划不能改变仓库既有执行通道：

- 浏览器操作仍只能通过 ZClaw bridge。
- 不新增 Playwright/Selenium/Puppeteer/browser-use。
- 不打开本机浏览器。
- 不臆造 ZClaw 工具名。
- 不修改 `packages/zclaw` 的路径白名单。

节奏层只决定“何时执行、是否允许执行、执行前后如何验证”，不改变“通过什么通道执行”。
