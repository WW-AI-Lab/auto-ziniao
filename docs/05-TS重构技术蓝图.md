# TypeScript 重构技术蓝图

> 目标：将紫鸟自动化引擎从 Python 运行时迁移到 TypeScript/Node.js，同时保持现有 flow 资产、ZClaw 安全边界、自愈闭环、WebAdmin 与 OpenClaw 集成能力兼容。本文是实施前的技术蓝图，不是当前运行规范。

## 结论先行：能否完全去除 Python 依赖

可以，但前提是迁移范围必须覆盖三个层面：

1. **核心引擎迁移**：`engine/` 下的 `zclaw_client.py`、`flow_engine.py`、`self_heal.py`、`manager.py` 全部迁移为 TS/Node.js。
2. **WebAdmin 后端迁移**：当前 `webadmin/` 后端是 FastAPI + uvicorn，必须替换为 TS Web 服务，否则运行 WebAdmin 仍需要 Python。
3. **开发与验证脚本迁移**：现有测试、校验、启动命令、回滚验证不能再依赖 `python3 manager.py`。旧入口可以保留为过渡 wrapper，但最终版本应删除或仅作为历史兼容分支，不作为生产路径。

完全去除 Python 后，运行时依赖会变为：

- Node.js LTS；
- npm/pnpm 安装的 TS 编译产物依赖；
- 本地紫鸟客户端及 ZClaw bridge；
- 可选的 OpenClaw/Claude/Cursor Agent CLI；
- SQLite 数据库文件（由 Node sqlite 驱动访问）。

如果选择保留当前 FastAPI WebAdmin，则只能做到“核心引擎去 Python”，不能做到“项目完全去 Python”。

## 当前系统画像

### 核心闭环

当前项目由三态闭环构成：

1. **沉淀**：Agent 经 ZClaw bridge 跑通任务，将步骤固化为 `flows/*.json` + `extracts/*.js`。
2. **常态执行**：`manager.py run <flow>` 以 0 tokens 执行 flow，产出写入 `data/output/`，日志写入 `data/logs/runs.jsonl`。
3. **异常自愈**：流程失败后截图、分类、匹配 `known_issues`、冷却判断、组装提示词并调用 Agent CLI。

### 关键模块

| 模块 | 当前实现 | 迁移目标 |
|------|----------|----------|
| CLI 入口 | `manager.py` → `engine/manager.py` | `packages/cli`，保留命令兼容 |
| ZClaw 客户端 | `engine/zclaw_client.py` | `packages/zclaw`，唯一 ZClaw 网络出口 |
| Flow 引擎 | `engine/flow_engine.py` | `packages/flow-engine` |
| 自愈触发 | `engine/self_heal.py` | `packages/self-heal` |
| 路径常量 | `engine/paths.py` | `packages/core/paths` |
| WebAdmin 后端 | FastAPI + SQLite | Node Web API + SQLite |
| WebAdmin 前端 | React + Vite + TS | 保留并重整到 monorepo |
| OpenClaw 集成 | CLI 模板 + gateway 探测 | 独立 `packages/openclaw` |
| 流程资产 | `flows/*.json`、`extracts/*.js` | 原格式兼容 |

### 最高安全边界

迁移后必须继续满足：

- 所有浏览器操作只能经 `http://127.0.0.1:9481/zclaw/*`；
- 唯一调用入口仍是 `POST /zclaw/tools/invoke`；
- 禁止本机 Chrome/Safari/Edge/Firefox；
- 禁止 Playwright/Selenium/Puppeteer/browser-use；
- bridge 不可达时停止任务并报告环境问题，不允许 fallback 到其他浏览器方案；
- 工具名只能来自 `GET /zclaw/tools` 或已确认静态白名单，禁止臆造。

### 包职责

| 包 | 职责 | 依赖原则 |
|----|------|----------|
| `packages/core` | 路径、文件 IO、JSONL、时间、日志、错误类型、进程工具 | 只依赖 Node 标准库 |
| `packages/schemas` | Flow、RunLog、Heal、Schedule、Chat、OpenClaw 配置类型与 JSON Schema | 可用 `zod` 或 `typebox`，需生成 JSON Schema |
| `packages/zclaw` | ZClaw bridge client、工具发现、API key 加载、路径白名单 | 不依赖 Web/API 层 |
| `packages/flow-engine` | Flow 加载、静态校验、变量解析、条件、步骤执行、输出、运行日志 | M3 依赖 `core/schemas/zclaw`；self-heal 在 M4 接入 |
| `packages/self-heal` | 错误分类、模板渲染、冷却、known_issues、Agent 调用 | 依赖 `core/schemas/openclaw` |
| `packages/openclaw` | OpenClaw gateway、OpenClaw CLI、Agent adapter 抽象、skill 同步工具 | 不直接依赖 flow-engine |
| `packages/cli` | `ziniao` CLI，兼容当前 `manager.py` 命令 | 聚合核心包 |
| `apps/webadmin-api` | REST/SSE API、调度器、SQLite DAO、静态前端托管 | 不直接访问 ZClaw，只调用 CLI 或 flow-engine 服务层 |
| `apps/webadmin-frontend` | 现有 React/Vite 前端 | 复用现有页面与 API 类型 |

## 技术栈与框架选择

### 运行时

**选择：Node.js LTS + TypeScript**

理由：

- 前端已是 TS，统一语言降低维护成本；
- Node 标准库可覆盖文件、子进程、HTTP、stream、定时器等核心能力；
- ZClaw bridge 是本地 HTTP API，Node 原生 `fetch` 足够；
- OpenClaw gateway 是 HTTP/SSE，Node 适合实现流式转发；
- TypeScript 类型系统适合把 flow DSL 契约前置。

### 包管理

**选择：pnpm workspace**

理由：

- monorepo 多包边界清晰；
- 磁盘占用低；
- workspace 协议便于内部包引用；
- 可集中执行 build/test/lint。

可替代方案：

- npm workspace：更通用，但多包管理体验弱一些；
- yarn：可用，但本项目没有必要引入额外团队习惯成本。

### 构建工具

**选择：tsup 或 tsx + tsc 双层策略**

- 开发运行：`tsx`；
- 类型检查：`tsc --noEmit`；
- 生产构建：`tsup` 输出 ESM/CJS 或仅 ESM；
- CLI 输出带 shebang。

### 测试框架

**选择：Vitest**

覆盖：

- schema 兼容；
- flow 静态校验；
- 变量解析；
- 条件表达式；
- branch/goto；
- validate 规则；
- ZClaw client 安全白名单；
- self-heal 错误分类与冷却；
- OpenClaw gateway/CLI adapter；
- Web API。

### Schema 与校验

**推荐：Zod + `zod-to-json-schema`**

理由：

- TS 类型与运行时校验同源；
- 易写默认值和兼容逻辑；
- 可导出 JSON Schema 给 WebAdmin 编辑器、Agent、OpenSpec 或外部工具使用。

注意：

- flow JSON 历史兼容优先；
- 新字段必须默认可选；
- 旧 payload 缺失数组时必须用 `?? []` 兼容；
- 对写操作、密码、token、cookie 等敏感字段要做业务校验。

### CLI 框架

**选择：commander**

命令兼容：

```bash
ziniao list
ziniao run <flow_id> [-p k=v]... [-v] [--no-heal]
ziniao run-all
ziniao retry <flow_id>
ziniao new <flow_id> [名称]
ziniao validate <flow_id>
ziniao history [flow_id]
ziniao enable <flow_id>
ziniao disable <flow_id>
ziniao heals
ziniao stats
ziniao cron
ziniao web
```

兼容期可提供：

```bash
python3 manager.py run orders_overview
```

但它只能作为过渡 wrapper。完全去 Python 前，需要把文档、crontab、WebAdmin 子进程全部切到 `ziniao` 或 `node dist/cli/index.js`。

### Web 后端

**推荐：Fastify**

理由：

- 性能好，插件生态稳定；
- 原生 schema 支持强；
- REST/SSE 实现直接；
- 比 NestJS 轻，适合本地单用户工具；
- 可明确禁止绑定 `0.0.0.0`。

可替代：

- Hono：更轻，适合 edge 风格，但 Node 本地服务和 SQLite 场景下 Fastify 更稳妥；
- Express：生态成熟，但类型和 schema 约束较弱；
- NestJS：结构强，但对本项目偏重。

### SQLite

**推荐：better-sqlite3**

理由：

- 同步 API 简单，适合本地单用户管理端；
- 调度器和 API 访问模式轻量；
- 可明确设置 WAL、busy timeout；
- 避免 ORM。

如果必须减少 native addon 风险，可选择：

- `node:sqlite`：取决于 Node 版本稳定性；
- `sqlite3`：异步回调/API 体验较差。

### 前端

**保留：React + Vite + TypeScript + antd + @ant-design/x**

迁移动作：

- 从 `webadmin/frontend` 移到 `apps/webadmin-frontend`；
- API 类型从 `packages/schemas` 生成或直接复用；
- dev proxy 指向 TS Web 后端；
- 构建产物由 `apps/webadmin-api` 托管。

### 日志与数据格式

继续使用：

- `data/logs/runs.jsonl`
- `learnings/heals.jsonl`
- `data/logs/heals/*.json`
- `data/logs/heals/*_prompt.md`
- `learnings/known_issues.json`
- `data/output/*`

这些是项目与 Agent 的长期契约，不建议在 TS 迁移中改成全 SQLite。

## 核心契约设计

### Flow Definition

TS 中应建模为：

```ts
type FlowDefinition = {
  id: string
  name: string
  version: number
  enabled: boolean
  schedule?: string
  description: string
  retry?: { maxAttempts?: number; delayMs?: number }
  params?: Record<string, unknown>
  steps: FlowStep[]
  on_success?: { close_store?: boolean }
  on_fail_final?: { notify?: boolean; close_store?: boolean; heal?: boolean }
  heal?: { hints?: string }
}
```

迁移要求：

- 当前 `flows/*.json` 不需要改；
- `params` 中 `_` 开头字段仍作为注释忽略；
- `store_name` / `store_id` 选择优先级不变；
- `@extracts/*.js` 引用规则不变；
- `validate` 规则语义不变；
- `on_fail` 五种策略不变。

### ZClaw 工具契约

工具名以 `GET /zclaw/tools` 为准，静态白名单仅作 bridge 不可查询时的文档参考，不允许用于臆造新工具。

TS client 必须提供：

- `getTools()`
- `invoke(tool, args, timeoutMs)`
- `listStores()`
- `openStore()`
- `closeStore()`
- `visit()`
- `executeScript()`
- `screenshot()`
- `click()`
- `waitElement()`

所有高级封装最终只能调用：

```text
GET  /zclaw/tools
POST /zclaw/tools/invoke
```

### Self-Heal 契约

保持现有行为：

- 错误类型：`nav_failed`、`extract_failed`、`element_not_found`、`timeout`、`auth_failed`、`bridge_down`、`generic`；
- 模板查找顺序不变；
- `heal.hints` 注入提示词；
- `known_issues.json` 命中后不触发 Agent；
- 同流程同步骤冷却；
- 单流程每日上限；
- 失败时尽力截图；
- 修复闭环仍要求 validate、run、写 known_issues。

## OpenClaw 集成设计

### 集成目标

TS 迁移后，OpenClaw 需要支持三类能力：

1. **自愈 Agent 调用**：流程失败时自动调用 OpenClaw  gateway。
2. **WebAdmin Chat**：在 Web 管理界面中进行会话式 Agent 对话。
3. **Skill/工作区同步**：将 repo-local 紫鸟 skill 同步到 OpenClaw 工作区，保障 Agent 使用同一套操作规范。

### Agent Adapter 抽象

```ts
interface AgentAdapter {
  name: string
  send(input: {
    sessionKey: string
    message: string
    timeoutMs?: number
  }): AsyncIterable<AgentEvent>
}

type AgentEvent =
  | { type: 'delta'; text: string }
  | { type: 'reasoning_delta'; text: string }
  | { type: 'tool_call'; name: string }
  | { type: 'done'; content: string }
  | { type: 'error'; message: string }
```

### OpenClaw 集成优先级

不要把 `POST /v1/chat/completions` 作为首选集成方式。它是 OpenClaw gateway 提供的 OpenAI-compatible HTTP 兼容面，适合让现有 OpenAI SDK/工具临时接入，但不是最原生的 OpenClaw 控制面。

推荐优先级：

1. **OpenClaw App SDK（首选）**  
   使用 `@openclaw/sdk` 连接 gateway WebSocket，调用 `Agent.run()`、`Run.events()`、`Run.wait()`、`Run.cancel()`、`Session.send()` 等高级 API。它是外部 app/script/dashboard/CI/IDE extension 面向 OpenClaw 的官方客户端抽象，负责封装 gateway RPC、事件归一化、run 等待与取消。
2. **Gateway WebSocket RPC（次选）**  
   如果 SDK 版本、发布方式或依赖边界暂时不适合引入，则直接实现 gateway WS RPC client。核心方法包括 `chat.send` / `agent.wait` / `chat.abort` / `sessions.send` / `sessions.abort` / `chat.history`。这仍然是 OpenClaw 原生控制面。
3. **OpenClaw CLI（稳定兜底）**  
   对自愈这类后台任务，可继续使用 `openclaw agent --session-key ... --message ... --json --timeout ...`。CLI 是官方稳定封装，缺点是流式事件和工具事件不如 SDK/RPC 细。
4. **OpenAI-compatible HTTP（最后兜底）**  
   `POST /v1/chat/completions` 和 `POST /v1/responses` 只作为兼容路径。它们默认可能关闭，且 HTTP bearer 认证近似 gateway operator 全权限，权限边界比 scoped WebSocket RPC 粗。

### OpenClaw App SDK Adapter

行为：

- 读取 `~/.openclaw/openclaw.json` 中的 gateway 端口、bind、auth mode；
- token 只在进程内使用，不写日志、不回传前端；
- 连接 `ws://127.0.0.1:<gateway.port>`；
- 用 `OpenClaw` client 建立连接；
- 自愈场景优先用 agent run：
  - `oc.agents.get(agentId)`；
  - `agent.run({ input, sessionKey, timeoutMs })`；
  - `run.events()` 转换为 WebAdmin SSE；
  - `run.wait()` 获取最终状态；
  - 超时或用户取消时 `run.cancel()`；
- WebAdmin chat 场景优先用 session：
  - `oc.sessions.create()` 或按既有 sessionKey 解析；
  - `session.send(message)`；
  - `run.events()` 流式返回；
  - `run.wait()` 落库最终状态。

建议 sessionKey：

| 场景 | sessionKey |
|------|------------|
| 自愈 | `ziniao-heal:<flow_id>` 或 `agent:<agentId>:ziniao-heal:<flow_id>` |
| WebAdmin Chat | `ziniao-webadmin:<session_id>` |
| 调试/一次性任务 | `ziniao-debug:<timestamp>` |

### Gateway WebSocket RPC Adapter

当不使用 SDK 时，直接走 gateway 原生 RPC：

1. 握手连接：
   - WebSocket text JSON frames；
   - 首帧发送 `connect`；
   - 声明 role、scopes、client 信息与 token；
   - 只请求最小必要 scopes，例如 `operator.read`、`operator.write`。
2. 启动运行：
   - `chat.send`：
     ```json
     {
       "sessionKey": "ziniao-webadmin:<session_id>",
       "message": "...",
       "timeoutMs": 300000,
       "idempotencyKey": "<run-id>"
     }
     ```
   - 返回中提取 `runId`。
3. 监听事件：
   - 订阅 gateway 事件；
   - 按 `runId` 过滤；
   - 将 assistant delta、thinking、tool、approval、lifecycle 转换为 WebAdmin SSE。
4. 等待终态：
   - `agent.wait`：
     ```json
     { "runId": "<run-id>", "timeoutMs": 300000 }
     ```
   - wait deadline 到期但 run 仍活跃时，不要等同于任务失败，应继续轮询或显示 running/accepted。
5. 取消：
   - `chat.abort` 或 `sessions.abort`，按 `runId` 和 `sessionKey` 取消。

该方式比 OpenAI HTTP 更贴近 OpenClaw：能看到 run lifecycle、工具调用、approval、artifact、task 等 OpenClaw 原生事件。

### OpenClaw CLI Adapter

行为：

- 命令模板继续来自 `config.json` 的 `heal.agents.openclaw.command`；
- `{prompt}`、`{prompt_path}`、`{session_key}`、`{flow_id}`、`{heal_id}` 占位符继续支持；
- WebAdmin chat 场景要移除 `--deliver` / `--channel`，避免聊天消息被投递到飞书等外部渠道；
- 自愈场景可以保留现有投递策略。

### OpenAI-compatible HTTP Adapter

仅作为兼容兜底：

- `POST http://127.0.0.1:<gateway.port>/v1/chat/completions`；
- `POST http://127.0.0.1:<gateway.port>/v1/responses`；
- 需要 gateway 配置显式启用对应 HTTP endpoint；
- bearer token 来自 gateway auth；
- `stream: true` 时解析 SSE；
- chat completions 可通过 `user` 字段隔离会话，但语义仍是 OpenAI 兼容层；
- responses 可通过 `x-openclaw-session-key` 之类的 header 承载 OpenClaw session 语义；
- 404、连接拒绝、未配置 token、endpoint 未启用时，应回退到 SDK/RPC/CLI，而不是修改用户配置。

安全注意：

- Gateway HTTP bearer auth 近似 operator 全权限，不适合作为默认 WebAdmin 后端常驻密钥面；
- 不在前端暴露 gateway token；
- 不自动修改 `~/.openclaw/openclaw.json` 去开启 HTTP endpoint；
- 不把 HTTP 兼容层作为 OpenClaw 能力边界的唯一抽象。

### Skill 同步

建议新增命令：

```bash
ziniao openclaw sync-skill --target ~/.openclaw/workspace-ziniao/skills/ziniao-assistant
ziniao openclaw check
```

同步规则：

- repo-local skill 是源；
- 同步前验证 `SKILL.md`、`references/flow-distill.md` 存在；
- 清理 `.DS_Store`、`.openclaw`、临时文件；
- 不同步任何凭证；
- 同步后输出目标路径和文件清单。

## 完整迁移规划

### 第 0 阶段：建立 OpenSpec 变更

建议 change 名称：

```bash
openspec new change rewrite-engine-in-typescript
```

产物：

- `proposal.md`：为什么迁移、范围、非目标；
- `design.md`：本蓝图精简成可执行设计；
- `tasks.md`：分阶段任务；
- 必要时新增 spec：`typescript-runtime`、`zclaw-safety`、`flow-engine-compatibility`、`openclaw-integration`。

验收：

```bash
openspec validate --changes --strict
```

### 第 1 阶段：契约冻结与测试样本

任务：

- 枚举所有现有 flow；
- 为每个 flow 建立静态校验样本；
- 固化变量解析、branch、validate、on_fail 的 golden tests；
- 记录当前 CLI 输出关键字段；
- 定义 schema 包。

交付：

- `packages/schemas`；
- `test/fixtures/flows/*`；
- `test/golden/*`；

验收：

- 所有现有 flow 可被 schema 解析；
- 未声明参数只 warning，不破坏旧行为；
- 缺失可选数组不崩溃。

### 第 2 阶段：TS 基础设施

任务：

- 新增 `package.json`、`pnpm-workspace.yaml`、`tsconfig.base.json`；
- 建立 `packages/core`；
- 建立 build/test/lint 命令；
- CI 或本地脚本增加 `pnpm test`、`pnpm build`。

验收：

- `pnpm install`；
- `pnpm build`；
- `pnpm test`。

### 第 3 阶段：迁移 ZClaw Client

任务：

- 实现配置读取；

- 实现高级封装；
- 实现错误类型；

### 第 4 阶段：迁移 Flow Engine

任务：

- 迁移 flow 加载；
- 迁移 `validateFlow`；

## 安全与凭证

## 风险与应对

| 风险 | 影响 | 应对 |
|------|------|------|
| 一次性翻译导致行为漂移 | flow 运行结果不一致 | golden tests + 双跑 |
| WebAdmin 后端迁移扩大范围 | 周期变长 | 先切 CLI 子进程，再迁 API |
| Node SQLite native 依赖安装失败 | WebAdmin 不可用 | 评估 `node:sqlite` fallback |
| OpenClaw gateway 版本差异 | chat 不可用 | gateway 探测失败自动 CLI 回退 |
| 自愈提示词丢上下文 | Agent 修复质量下降 | prompt 生成 golden tests |
| 安全出口被绕过 | 严重事故 | 静态扫描 + 单测 + code review 阻断 |
| 文档命令未同步 | 用户仍依赖 Python | 最终阶段全仓扫描 `python3` |

### M1 回滚方式

M1 不改变 Python 执行链路。需要回滚时，删除根级 Node workspace 文件（`package.json`、`pnpm-workspace.yaml`、`tsconfig.base.json`、`vitest.config.ts`、`pnpm-lock.yaml`）、`packages/`、`test/` 下 TS baseline fixtures/tests、`scripts/validate-python-flows.ts`、`scripts/security-scan.ts` 即可。`engine/`、`manager.py`、`flows/`、`extracts/`、`data/`、`learnings/` 不需要迁移回滚。

### M2 回滚方式

M2 不改变 Python 执行链路。需要只回滚 M2 时，删除 `packages/zclaw`，并恢复 root `package.json` 的 `build`/`typecheck` 范围、`tsconfig.base.json`/`vitest.config.ts` alias 与 `scripts/security-scan.ts` 的 allowlist。回滚后 `python3 manager.py list` 与 `python3 manager.py validate orders_overview` 仍应可运行。
